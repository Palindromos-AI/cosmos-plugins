# ZSXQ Fetch

Collect one named Knowledge Planet's complete Beijing calendar day of topics from all authors into one reader-facing Markdown file. Preserve source meaning and wording; do not summarize or analyze it. Keep verification evidence in a temporary internal audit ledger, never in the reader report.

Judge completeness by content coverage and extraction accuracy, not by source quality. Apply this rule equally to topic bodies, images, linked web pages, and PDFs: resolution, encoding, transport form, rendering path, and whether the bytes are the publisher's original file do not affect completeness when all substantive content is readable, fully extracted, and verified. Treat partial, truncated, missing, or uncertain content as failed.

## Runtime split

- Use the signed-in browser only for authentication-bound discovery, navigation, expansion, exact source capture, and visual judgment. Navigate Knowledge Planet sequentially.
- In the persistent Chrome-control session, import `collectZsxqTimelineRangeWithAutoRepair` and `collectZsxqDetailWithAutoRepair` from `scripts/zsxq-browser-collector.mjs`. These Node wrappers drive the existing authenticated tab without launching a browser, reading session storage, or calling a private API. They centralize the versioned DOM adapter, condition-based mounting checks, collapsed-body expansion, sequential scrolling, exact author/time/body/attachment association, image source and dimension inventory, non-pinned chronology, date-boundary proof, automatic repair handoff, and resumable `browser-collector-checkpoint.json`. Page-evaluation functions only observe structure and geometry; exact browser locators perform expand clicks and a real `End` key performs pagination, with count-based bounded retries. Submit the returned `coverage` and runner-ready `inventory`; keep `browser_assets` only as exact capture inputs inside the run workspace.
- Use `scripts/zsxq-dom-extractor.mjs` for every Knowledge Planet topic body, including linked Knowledge Planet topic pages. Resolve the bundled script to an absolute path and import `waitForZsxqDetailReadyOnTab`, `waitForZsxqDetailReady`, and `extractZsxqTopicBodies` into the persistent browser-control session. After each detail-page navigation, call `waitForZsxqDetailReadyOnTab(tab, { expectedTopicCount: 1, expectedImageCount })`; the Node-side wrapper re-enters page evaluation only when a redirect destroyed the inspected context, while preserving one five-second total deadline and rethrowing every unrelated error. It passes `waitForZsxqDetailReady` directly to the page-evaluation API. Supply `expectedImageCount` only when the exact `.topic-detail-panel app-talk-content img` element count was established independently; it is a DOM-readiness constraint, not the later semantic child-inventory count. Otherwise omit it and still prove the final child range separately. The page helper requires exactly one detail panel, the expected topic roots and dedicated bodies, and a loaded non-broken image set; the actual body text plus every image source, dimensions, and load state must remain unchanged for two samples. Never replace this readiness contract with a fixed delay. On timeout, stop that page as a readiness failure instead of calling the extractor against a partially mounted DOM. Then pass `extractZsxqTopicBodies` directly to the page-evaluation API with `{ expectedTopicCount }`. Establish that expected count independently from the ordered topic metadata containers already used for inventory; use `1` for a verified single-topic detail page and `0` only for a separately proven zero-topic range. The extractor reads only one `.talk-content-container > .content` inside each `app-talk-content`; never substitute `app-talk-content.innerText`, `.talk-content-container.innerText`, or another ancestor fallback.
- Use Node.js 22.13 or later and `scripts/zsxq-runner.mjs` as the sole owner of persistent run state, inventory comparison, identities, keys, hashes, cache admission, PDF page coverage, completeness, audit rendering, reader rendering, and safe output replacement. Node 22.13 is the first 22.x release where `node:sqlite` no longer needs the `--experimental-sqlite` flag. Its built-in SQLite transactions admit one writer per run and one writer per canonical output path; both are released by the operating system after a process crash.
- Use `scripts/zsxq-image-tiles.mjs` only when a captured image is readable at native pixels but too dense to verify reliably as one whole image. It uses `sharp` to normalize orientation and crop lossless overlapping PNG tiles without resizing or inventing pixels. Sharp is deliberately lazy and optional for every ordinary runner command. Before the first tiled image in an independently installed skill, if the local runtime is absent, request permission and run `npm install --omit=dev` inside the `zsxq-fetch` directory; its package and lockfile pin the runtime. The runner, not the browser agent, validates tile geometry and the file-hash binding: the manifest source must equal the recorded representation byte-for-byte, and every normalized image and tile must match its recorded dimensions and SHA-256.
- Use `scripts/zsxq-single-asset-export.mjs` only for acquisition-ladder step 3. Invoke it once per exact frozen `transport_url`; it enforces one abortable request, media type and byte limits, workspace-contained atomic output, and a result with `remote_export_attempts: 1` plus `remote_export_batch_size: 1`. Never pass a page-wide asset list or reuse its result for a different attachment. After export, compare the representation visually with that exact attachment's topic-local slot before accepting it; matching dimensions alone are not source-association proof.
- Before starting a run, read `references/runner-contract.md` completely. It defines the CLI lifecycle and browser-to-runner JSON records. Do not edit `manifest.json`, the audit ledger, or the reader report by hand.
- Never let `zsxq-runner.mjs` control Chrome, inspect browser storage, or call Knowledge Planet endpoints. The browser collector may orchestrate only the already-authorized tab through the browser-control API. Node.js replaces repetitive navigation and deterministic bookkeeping, not authentication or image understanding.

## Required workflow

### 1. Resolve the workspace and request

- Read `<plugin-dir>/references/workspace-runtime.md` completely, then run `node <plugin-dir>/scripts/workspace-runtime.mjs show-config`. Configure only after the user explicitly confirms a durable root. Use the returned `<sources-workspace>` for the final report while keeping the private runner workspace temporary.
- Refuse an explicit output path outside `<sources-workspace>/output/zsxq`. Marketplace, plugin, and Skill updates never own or alter the binding or durable workspace.

- Require an exact planet name. Ask the user if it is missing or ambiguous.
- Resolve the exact named planet through the user's signed-in Knowledge Planet UI and record its canonical group URL. If multiple accessible planets share the name or the name cannot be resolved uniquely, ask the user instead of guessing. Honor an explicit planet URL only as disambiguating context; never require an owner name.
- Interpret every requested date and “today” in `Asia/Shanghai` (`UTC+08:00`), with one day running from Beijing `00:00:00` through the instant before the next Beijing midnight. Honor an explicit date; otherwise call the bundled `currentBeijingDate()` helper in `scripts/zsxq-time.mjs` to resolve the current Beijing calendar date. Treat Knowledge Planet's displayed timestamps as Beijing time and fail closed if visible platform evidence contradicts that contract. Record the resolved `YYYY-MM-DD`; never substitute the computer, browser, user-location, or publisher timezone.
- Default the output to `<sources-workspace>/output/zsxq/YYYY-MM-DD-<planet>.md`; honor only a workspace-contained explicit output path.
- Replace `/`, `\`, and control characters in the planet-derived filename with `-`.
- Include every topic published in the resolved planet on the requested date, regardless of author, and preserve each topic's exact displayed author. Exclude comments, replies, likes, and other interactions.
- Do not schedule future runs or add a generated summary.

### 2. Use the authenticated browser safely

- Follow the available Chrome-control skill and operate the user's existing signed-in Chrome session.
- Never inspect or export cookies, local storage, browser profiles, passwords, or session files.
- If Chrome is not connected or Knowledge Planet requires authentication, stop and ask the user to connect Chrome or sign in there. Do not bypass authentication with search results, previews, another account, or a private API.
- Keep the remote session read-only: do not post, comment, react, follow, edit, or delete anything.
- Always use the collector's `WithAutoRepair` exports in a skill run. DOM-contract failures and internal runtime reference failures return `automatic-repair-required`; invalid input, permission, authentication, browser-connection, and external-service errors remain direct actionable errors because adapter repair cannot resolve them. When automatic repair is required, immediately show the returned `notification` as a non-blocking progress update, retain the workspace, read `references/browser-repair-playbook.md` completely, diagnose and repair from evidence, run every required validation, and resume from the retained browser and runner checkpoints. Do not pause for repair approval. Repair permission never grants permission to commit, merge, push, publish, install dependencies, bypass access controls, or make unrelated changes; obtain any separately required authorization for those actions.
- Create a private temporary parent directory, choose a unique child path that does not yet exist, and pass that child to the runner's `init` command; the runner atomically creates and owns the workspace. Never pass an existing empty directory or symbolic link. Store the inventory, raw attachment transport URLs, extracted working text, internal audit ledger, content cache, and any downloaded or captured source representation there. Every JSON input and referenced representation must resolve inside this workspace; do not use a symbolic link to an outside path. Use `assets/extraction-audit-template.md` for the temporary audit ledger and never place it in `output/`. The runner removes the marked temporary directory after successful verification; on failure, retain it only when it helps diagnosis and report its path without exposing signed URL parameters.

### 3. Prove timeline coverage

- In the official UI, inspect and clear stale searches, tags, “只看星主”, member filters, and every other topic filter so the timeline includes every author's topics. Only after that visible confirmation, call `collectZsxqTimelineRangeWithAutoRepair` with `filtersClearedConfirmed: true`, the exact planet name, canonical group URL, Beijing platform date, runner workspace, and the live tab. Never set the flag merely to bypass `needs-filter-confirmation`; that status means the browser inventory is not allowed to start. Return to the true timeline top through this collector. It verifies the displayed name, expands only geometrically truncated target-date bodies, follows the non-pinned append-only stream, inventories exact topic-local images, links, and strict PDF file cards in DOM order, and scrolls until either the oldest stable timestamp is below the requested date or one exact direct `没有更多了` marker proves the absolute end of the finite timeline. A visible file gallery with no exact items, an item without one direct PDF indicator and one non-empty `.pdf` filename, or a file card that also contains an anchor is a contract failure rather than zero or duplicate attachments.
- When the collector returns `needs-top-confirmation`, visually load or dismiss every pending new-content batch through the official UI, confirm none remains, then rerun it with `topBoundaryConfirmed: true`. Never infer this confirmation from elapsed time or set the flag merely to continue. This establishes the verified upper boundary. A visible top newer than the target date is already a sufficient upper bound because pending items can only be newer. A visible top equal to or older than the target date requires this confirmation first; only afterward may an older top prove a zero-topic target date.
- Require `status: complete` and proof that the stream crossed below the requested date before submitting the returned `coverage` and complete `inventory` object to the runner. Its exact top-level shape is `{ "topics": [...] }`; pass that object directly to `record-inventory`, never `inventory.topics`, and do not reconstruct or clean it by hand. Use the separate `browser_assets` records to target exact image capture; signed sources remain in the temporary workspace.
- After expansion, capture bodies with `extractZsxqTopicBodies` using the collector's timeline-scoped talk selector and sticky-ancestor exclusion; associate its `dom_index` with the same ordered non-pinned `app-talk-content` occurrence used for topic metadata. Require its root count to equal the independently observed non-pinned topic-container count, require exactly one direct `.content` child per root, and require no `.showAll` descendant inside that body. The sibling `.showAll` control may display `展开全部` or `收起`; it is interface state and must never enter the body payload. Do not remove those words by global or line-based string replacement because identical text inside `.content` is legitimate source content. If any count or structure check fails, enter the automatic repair workflow before freezing inventory rather than falling back to a broader ancestor.
- Record each topic's displayed author exactly as provenance; never use author as an inclusion filter. Treat pinned older topics by their publication timestamp, not their screen position.
- Inventory every matching topic and top-level attachment before extracting attachments. Submit the collector's complete source-inventory object described in `references/runner-contract.md` once with `record-inventory`; the accepted top-level inventory is frozen, so start a new run rather than replacing it if that inventory was wrong. Do not start attachment extraction until the runner accepts it. Supply the raw stable platform identifier or permalink and let the runner give each topic a `topic_key`; if neither exists, it uses the source-order ordinal plus full timestamp. Persist the exact displayed author, full timestamp, permalink, `body_status` (`present`, `empty`, or `failed`), and unchanged working body text. Convert every explicit timestamp offset to `Asia/Shanghai` before determining its calendar date; every topic must fall on the requested Beijing date and the inventory must be newest first by instant. For `present`, the runner stores SHA-256 of the body's exact UTF-8 bytes; for `empty` or `failed`, it must store no body hash.
- Establish each topic's independent `image_count` and `image_count_evidence` from its fully expanded attachment slots, a complete detail view, a viewer counter such as `1/N`, or another UI signal that proves the end of the image set. Assign each top-level image an `image_ordinal` within that topic and open or enumerate every slot until the ordered image ordinals equal `1..image_count`. Keep `source_ordinal` as the image's position among all attachment types; it may differ from `image_ordinal` when images, webpages, and PDFs are interleaved. For zero images, confirm the fully expanded topic exposes no image slot. Do not infer the total from a page-wide asset list or from only the images that have already rendered. An unknown, conflicting, missing, duplicate, or out-of-range image slot makes the topic incomplete.
- Persist each attachment as a separate inventory entry with topic type, source ordinal, filename when exposed, stable platform identifier when available, and a transient `transport_url` when downloading requires one. Supply every available raw value to the runner. It derives `sanitized_source_url` by removing the complete query and fragment from an image or PDF transport URL; keep the full transport URL only in the temporary workspace and never place any transport or asset URL in the reader report. The runner records SHA-256 for every referenced local binary. Derive `source_identity` through the runner from the first available value in this order: stable platform identifier as `platform-id:<exact-id>`, SHA-256 of the transport URL's exact UTF-8 bytes as `url-sha256:<hex>`, downloaded binary SHA-256 as `binary-sha256:<hex>`, then `no-source-identity`. Never provide a precomputed identity or use a lower-priority identity when a higher-priority value is available.
- Associate every top-level image with one inventoried target-date topic before acquiring it. Prove the association from that topic's own container, permalink/detail view, attachment order, or equivalent visible UI relationship. Never treat a page-wide asset inventory, a shared `images.zsxq.com` host, or the current scroll viewport as proof that an image belongs to the requested date. Exclude assets belonging to older or newer topics, avatars, group artwork, navigation, controls, and other interface chrome before any screenshot or export.
- Derive every occurrence key as `<topic_key>:<type>:<source_ordinal>:<source_identity>` through the runner. It uses this as `attachment_key` even when the same platform ID, URL, or binary appears in another topic. Counts or arbitrary keys alone are not coverage proof.
- Within a linked page's main content, inventory every substantive inline image and directly embedded PDF as a child of that page attachment. For a Knowledge Planet detail link, call `collectZsxqDetailWithAutoRepair`; internally it must complete `waitForZsxqDetailReadyOnTab` before reading metadata, prove that the final canonical topic ID equals the requested mweb/canonical topic ID, then perform collapsed-body expansion, a detail-scoped dedicated-body cross-check, and exact image plus PDF file-card inventory before returning. Include every returned `files` entry in that page's child inventory in `dom_ordinal` order; a detail page's strict PDF cards are embedded children, never ignorable decoration. During that page's single visit, first prove the complete child count and page-end/main-content evidence, then submit the occurrence once through `record-web-inventory` before extracting the page body or any child. Submit a zero count and explicit evidence only for a verified child-free page. If access control or a loading failure prevents proving the complete child range, omit the count and submit `inventory_failure` with a concrete failure reason and localized reader note; include any known recovered children, but never convert an unknown range into zero. The runner keeps that page incomplete and out of cache. Derive each later extracted child's `embedded_media_key` as `<parent_attachment_key>:embedded-<type>:<source_ordinal>:<source_identity>`. Treat decorative icons, avatars, navigation graphics, ads, and recommendation thumbnails as interface noise rather than embedded media. Do not recursively follow new hyperlinks discovered inside the linked page.
- If the newest boundary cannot be established, the timeline cannot load far enough, chronology is inconsistent, or access hides an unknown number of topics, stop without creating or replacing the final file. Report why completeness cannot be established.
- A verified zero-topic day is valid only after crossing below the requested date.
- Submit the visible boundary evidence through `record-coverage`. A false coverage field requires a specific failure reason; `finalize` then fails closed and writes no report.

### 4. Minimize repeated work

- Treat browser navigation as the scarce step. When opening a linked page, expand through the complete main-content boundary, submit its frozen child inventory, then capture its body, metadata, and exact assets before navigating away. The inventory call and extraction remain separate runner states but occur during one browser visit. Do not revisit that page solely to collect information or assets that were available during the first visit.
- Treat a browser asset list as inventory, not as a download queue. Never call an asset bundle with more than one remote image asset ID, never bulk-export every image on a page, and never select image downloads only by host, filename pattern, or rendered dimensions. Use a remote acquisition route only when the active tool provides an enforceable per-call deadline or cancellation. A request timeout that cannot cancel the underlying remote fetch is not enforceable.
- Use this per-image acquisition ladder: (1) the rendered topic preview or a locator screenshot of that exact image; (2) after one click into the platform image viewer, a locator screenshot of the clearer rendered image, but reject a saved screenshot if the open viewer's exact image source and topic-local ordinal were not rechecked after the click; (3) one exact single-asset export through `scripts/zsxq-single-asset-export.mjs`, whose abort signal cancels the underlying fetch. Stop acquiring at the first representation whose native pixels contain the needed information. If a clearer attempt fails or times out, do not retry alternate signed URLs, original-file variants, or equivalent transformations; retain the best already captured representation.
- Compare the image's native pixel dimensions with its rendered CSS dimensions. When the native image contains small or dense text but whole-image visual verification remains uncertain, run `scripts/zsxq-image-tiles.mjs` against that exact workspace-local representation. This tile pass is mandatory before failure: never mark an image failed for small, dense, or compressed text while its native pixels have not yet been read tile-by-tile; only when the ordered tile reading still leaves content unreadable may the image be recorded as failed. Use the default `512×768` maximum tile size and `96px` overlap unless the source structure requires a smaller deterministic tile; never use a maximum above 512px wide or 768px high, custom overlap must stay positive and smaller than both tile maxima, and the plan may never exceed 512 tiles; never upscale, sharpen, denoise, hallucinate, or otherwise manufacture pixels. Read every tile once in row-major order, reconcile duplicated text only inside the overlap, and merge the semantic payload in natural reading order. Submit `tile_manifest_path` plus one ordered `tile_verifications` entry for every planned tile. If any tile remains unreadable, mark the image failed rather than treating the other verified tiles as complete.
- Keep one in-run binary cache in the temporary directory through the runner's `cache-lookup` command. Reuse image or PDF extraction only when the captured representation SHA-256 or downloaded binary SHA-256 matches and the cached extraction is complete and verified; never reuse a failed, partial, or uncertain result. There is no page cache: a repeated linked page is simply revisited and extracted again. Keep every occurrence-specific topic, attachment, and child key in the audit ledger even when its verified payload is reused.
- Navigate authenticated pages sequentially so the browser session and timeline state remain deterministic. After source assets are local, process independent images and PDF pages in bounded parallel batches when the available tools support it; hash and verify each result separately before accepting it.
- On a clearly blocked external page, stop retrying after the normal clean-page route and the one permitted browser route have both produced the same access-control result. Record the failure and continue with the remaining inventoried content.
- These optimizations may remove duplicate navigation, download, OCR, and hashing work only. They must never reduce the inventory, skip an attachment, weaken verification, or change the one-level linked-page boundary.

### 5. Extract each topic in source order

Process the inventoried topics newest first, matching their source order.

After freezing every linked-page child inventory for the topic and finishing all top-level and embedded extraction, write its JSON record according to `references/runner-contract.md` and submit it with `upsert-topic`. The runner accepts only the next source-order topic or a correction to the latest topic, compares it with the independent top-level and webpage-child inventories, hashes every referenced workspace file and payload, and atomically checkpoints the manifest. Use an ISO-8601 topic date-time with an explicit `Z` or numeric UTC offset; the runner converts the represented instant to `Asia/Shanghai` for date membership, so the host timezone never affects the result. Use `status` after each topic; `pending_web_inventory_count` identifies child inventories still needing a one-time record and `next_topic_source_order` identifies the resumable topic position.

For the topic body:

- Copy all visible text without summarizing, translating, correcting, or stylistically rewriting it.
- Copy only the exact `body` returned by `extractZsxqTopicBodies`. Before `record-inventory`, verify that any visible `.showAll` sibling is absent from that returned value by structure; never "clean" an already frozen body or let the runner infer whether a phrase is UI.
- Preserve headings, paragraphs, lists, quotations, and link targets when the source exposes them.
- Expand collapsed text before copying. Mark source text that is genuinely unreadable as `[无法辨认]`; never guess.
- Set `body_status: present` only after the complete displayed body has been captured. A lower-fidelity rendering is acceptable when every substantive character and structure is readable; a truncated, partially hidden, or uncertain body is `failed` regardless of how much text was recovered.
- When a body is `failed`, store any reliably recovered source fragment separately from `failure_reason`; store its exact UTF-8 `recovered_payload_sha256`, or no recovered hash with the literal `无可可靠恢复内容` when no fragment can be trusted. Never mix the failure explanation into the source payload.

For each image, in attachment order:

- Use any representation available through the platform's official UI that makes all substantive image content readable, including a preview, thumbnail, transformed image, browser-rendered image, or page screenshot. Prefer a clearer representation only when the current one leaves content unreadable or uncertain; do not spend time proving or retrieving the publisher's original binary when the complete content can already be verified.
- When a binary or screenshot is used, record that representation's exact pixel dimensions, SHA-256, and `representation_type` (`rendered-preview`, `locator-screenshot`, `viewer-screenshot`, `single-asset-export`, or `page-screenshot`). These fields identify the evidence used for extraction; they do not grade source quality and do not determine completeness.
- Extract the image's semantic content text in natural reading order: text a downstream reader needs to understand the information the topic author intended to share.
- Exclude unrelated interface chrome from the OCR payload, including operating-system status bars, clocks, signal or battery indicators, viewer controls, follow/share buttons, navigation labels, comment-input placeholders, and standalone like, favorite, share, or comment counts.
- Preserve a displayed account name or watermark that identifies the pictured source as `source_account` metadata; do not mix it into the OCR payload. Use `未显示` when no source account is visible.
- Keep interface text only when it is itself material evidence, such as a discussed button or setting, an error message, a transaction value, or a step in a tutorial. When uncertain, include text needed to understand the depicted content rather than deleting potentially substantive evidence.
- Preserve paragraph, list, and table structure where visible.
- Write `未检测到可读文字` when an image contains no readable text.
- Record a specific extraction failure instead of silently omitting an inaccessible or unreadable image.
- Perform a separate visual verification pass against the same representation used for extraction. Scan every content region in reading order and confirm that all substantive content is readable and captured, paragraph/list/table structure is preserved, `source_account` is separated, and unrelated interface chrome is absent. If the representation is too degraded, cropped, or obstructed to prove this, obtain a clearer representation; when the obstacle is small or dense text over sufficient native pixels, run the mandatory tile analysis before failing. Fail verification only after those paths are exhausted.
- For tiled analysis, perform that comparison against every lossless tile and require the runner's deterministic grid to cover the normalized source from edge to edge. Do not treat cutting a low-resolution preview into pieces as a clarity upgrade: tiling improves visual attention, not source information. Keep repeated overlap content once in the final OCR payload and record a specific per-tile verification note.
- Set `verification_status: verified` when that content comparison succeeds, regardless of the representation's quality or transport form. Otherwise set `verification_status: failed`, record the exact missing, unreadable, or uncertain content, and treat the document as incomplete. Keep `extraction_status: present` when a complete OCR payload exists and `empty` only when absence of substantive text was visually verified; partial OCR is `failed`, even if the recovered fragment is retained in an incomplete artifact.
- When an image representation exists, persist its exact oriented pixel dimensions and binary SHA-256 together with `extraction_status` (`present`, `empty`, or `failed`), `verification_status` (`verified` or `failed`), an exact `verification_note`, `source_account`, and the semantic-content OCR payload after interface-noise removal. For tiled analysis, also persist the generated manifest path and every ordered tile verification; the runner requires the manifest source to equal the representation byte-for-byte, reopens the normalized PNG and every tile, checks physical dimensions and SHA-256 values, and recomputes the deterministic grid. Do not hash excluded UI text. If no representation can be acquired at all, omit the representation path, dimensions, and representation type; record failed extraction and failed verification so the runner retains the known attachment as incomplete. For `present`, store the OCR payload's UTF-8 SHA-256; for `empty` or `failed`, store no text hash.
- For `failed`, persist any reliably recovered semantic-content fragment separately from `failure_reason`; store its exact UTF-8 `recovered_payload_sha256`, or no recovered hash with `无可可靠恢复内容` when none exists. Do not insert the failure explanation into the recovered source payload.

For each linked web page:

- Prefer the available clean-webpage extraction skill for public HTML pages. Use the authenticated browser only when the page requires its existing session or interactive rendering.
- Extract the article title, original linked URL, canonical URL when available, author/publication metadata when visible, and main body.
- Remove navigation, advertisements, cookie banners, recommendations, and unrelated comments.
- Preserve the page's semantic heading, paragraph, list, quotation, and table order.
- Use any accessible rendering of the linked page, including clean-page extraction, browser rendering, reader view, or screenshot/OCR. Do not substitute a search snippet or another publisher because neither proves the linked page's complete contents.
- Extract substantive inline images and directly embedded PDFs that belong to the page's main content, using the image and PDF rules above. Keep their payloads and evidence separate from the page's textual body. Ignore decorative or navigational media and do not recursively open hyperlinks found inside the page.
- Complete the page body and embedded-media inventory in the same browser visit whenever the UI exposes them together. Export the exact required media before leaving the page; use the in-run binary cache for identical image or PDF binaries instead of extracting them again.
- Persist a separate `web_body_status`, the exact working main-body payload, and its UTF-8 SHA-256 under the same `present`/`empty`/`failed` rules as image text. Use `web_body_status: present` only after the complete substantive textual body and its structure have been captured; a clipped, paginated-but-unloaded, paywalled, or otherwise partial body is `failed`.
- Persist the page's aggregate `extraction_status` as `present` only when `web_body_status` is `present` or `empty` and every inventoried embedded-media child is complete and verified. Set the page to `failed` when its body or any embedded child is failed, missing, partial, unreadable, or uncertain; retain any recovered fragments in the incomplete artifact.
- For a failed body or child, keep the reliable recovered source fragment, its applicable UTF-8 `recovered_payload_sha256`, and `failure_reason` as separate audit fields.

For each PDF:

- Follow the available PDF skill.
- Treat blocked inline viewing and blocked downloading as different states. When the official file preview exposes exactly one visible `下载文件` control for the inventoried filename, call `downloadZsxqTimelinePdfOnTab` for that exact topic and PDF occurrence, arm the browser download event before clicking, resolve the exact completed download rather than guessing from its filename, and copy it into the private runner workspace before parsing. A duplicate-name suffix in the browser download directory does not change the inventoried filename. Use only this official member UI; do not reverse-engineer private APIs. Record a document-level access failure only when neither an official download nor another complete accessible representation exists.
- Use whichever accessible PDF representation yields complete page contents: the text layer, rendered pages, screenshots, or OCR. Prefer the text layer for efficiency, then visually check or render any page whose extraction is missing, incomplete, or clearly corrupt. File fidelity and rendering quality do not affect completeness when every page's substantive content is fully readable.
- Establish the PDF's total `page_count` independently from a parser, document metadata, a viewer-reported total, or another reliable end-of-document signal, and record `page_count_evidence`. If the total cannot be established, sources disagree, or the viewer never proves its end, treat the PDF as failed rather than assuming the loaded pages are complete.
- Preserve page boundaries as `#### 第 N 页` for a top-level PDF and `##### 第 N 页` for a PDF embedded inside a linked page; maintain reading order.
- Record inaccessible, encrypted, corrupt, or unreadable pages explicitly.
- Persist one manifest entry per PDF page with `page_key`, page number, extraction status, exact working page payload, and UTF-8 SHA-256 for `present`. Require unique page numbers and an ordered page-number sequence exactly equal to `1..page_count`; a missing, duplicate, out-of-order, or out-of-range page makes the PDF failed. Validate pages individually; `present` means the complete substantive page content was captured, while any partial or uncertain page is `failed`. Do not hash headings or page separators as extracted text.
