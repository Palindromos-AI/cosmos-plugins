# ZSXQ Fetch

Collect one named Knowledge Planet's complete Beijing calendar day of topics from all authors into one reader-facing Markdown file. Preserve source meaning and wording; do not summarize or analyze it. Keep verification evidence in a temporary internal audit ledger, never in the reader report.

Judge completeness by content coverage and extraction accuracy, not by source quality. Apply this rule equally to topic bodies, images, linked web pages, and PDFs: resolution, encoding, transport form, rendering path, and whether the bytes are the publisher's original file do not affect completeness when all substantive content is readable, fully extracted, and verified. Treat partial, truncated, missing, or uncertain content as failed.

## Runtime split

- Use the signed-in browser only for authentication-bound discovery, navigation, expansion, exact source capture, and visual judgment. Navigate Knowledge Planet sequentially.
- In the persistent Chrome-control session, import `collectZsxqTimelineRangeWithAutoRepair` and `collectZsxqDetailWithAutoRepair` from `scripts/zsxq-browser-collector.mjs`. These Node wrappers drive the existing authenticated tab without launching a browser, reading session storage, or calling a private API. **The collector output is authoritative**: it owns the versioned DOM adapter and every timeline and detail proof obligation, enumerated in `references/runner-contract.md`. Submit the returned `coverage` and runner-ready `inventory` as-is; keep `browser_assets`, `pdf_download_targets`, and `skipped_topics` only as run-workspace inputs and reporting context.
- `scripts/zsxq-dom-extractor.mjs` is an internal implementation detail of the collector. Do not import it or re-run its checks manually, and never re-derive topic bodies or `image_count` by hand-written DOM inspection: a body or count the collector did not produce must never enter the runner.
- Use Node.js 22.13 or later and `scripts/zsxq-runner.mjs` as the sole owner of persistent run state, inventory comparison, identities, keys, hashes, cache admission, PDF page coverage, completeness, audit rendering, reader rendering, and safe output replacement.
- Use `scripts/zsxq-image-tiles.mjs` only when a captured image is readable at native pixels but too dense to verify reliably as one whole image; it crops lossless overlapping PNG tiles with `sharp` without resizing or inventing pixels. Sharp is lazy and optional for every ordinary runner command; its one-time installation always requires the user's approval and follows `references/runner-contract.md`. Use `scripts/zsxq-single-asset-export.mjs` only for acquisition-ladder step 3, once per exact frozen `transport_url`; never pass a page-wide asset list or reuse its result for a different attachment, and visually compare the exported representation with that exact attachment's topic-local slot before accepting it.
- Before starting a run, read `references/runner-contract.md` completely. It defines the CLI lifecycle, the browser-to-runner JSON records, and the safe output-replacement rules. Do not edit `manifest.json`, the audit ledger, or the reader report by hand.
- Never let `zsxq-runner.mjs` control Chrome, inspect browser storage, or call Knowledge Planet endpoints. The browser collector may orchestrate only the already-authorized tab through the browser-control API. Node.js replaces repetitive navigation and deterministic bookkeeping, not authentication or image understanding.

## Required workflow

### 1. Resolve the workspace and request

- Read `<plugin-dir>/references/workspace-runtime.md` completely, then run `node <plugin-dir>/scripts/workspace-runtime.mjs show-config`. Configure only after the user explicitly confirms a durable root. Use the returned `<sources-workspace>` for the final report while keeping the private runner workspace temporary.
- Refuse an explicit output path outside `<sources-workspace>/output/zsxq`. Marketplace, plugin, and Skill updates never own or alter the binding or durable workspace.
- Require an exact planet name. Ask the user if it is missing or ambiguous.
- Resolve the exact named planet through the user's signed-in Knowledge Planet UI and record its canonical group URL. If multiple accessible planets share the name or the name cannot be resolved uniquely, ask the user instead of guessing. Honor an explicit planet URL only as disambiguating context; never require an owner name.
- Interpret every requested date and “today” in `Asia/Shanghai` (`UTC+08:00`); honor an explicit date, otherwise resolve the current Beijing calendar date with `currentBeijingDate()` from `scripts/zsxq-time.mjs`, and record the resolved `YYYY-MM-DD`. Treat Knowledge Planet's displayed timestamps as Beijing time and fail closed if visible platform evidence contradicts that contract; never substitute the computer, browser, user-location, or publisher timezone.
- Default the output to `<sources-workspace>/output/zsxq/YYYY-MM-DD-<planet>.md`; honor only a workspace-contained explicit output path. Replace `/`, `\`, and control characters in the planet-derived filename with `-`.
- Include every topic published in the resolved planet on the requested date, regardless of author, and preserve each topic's exact displayed author. Exclude comments, replies, likes, and other interactions.
- Do not schedule future runs or add a generated summary.

### 2. Use the authenticated browser safely

- Follow the available Chrome-control skill and operate the user's existing signed-in Chrome session.
- Never inspect or export cookies, local storage, browser profiles, passwords, or session files.
- If Chrome is not connected or Knowledge Planet requires authentication, stop and ask the user to connect Chrome or sign in there. Do not bypass authentication with search results, previews, another account, or a private API.
- Keep the remote session read-only: do not post, comment, react, follow, edit, or delete anything.
- Always use the collector's `WithAutoRepair` exports in a skill run. DOM-contract failures and internal runtime reference failures return `automatic-repair-required` with the failure `code`, `phase`, and a sanitized diagnostic handoff; invalid input, permission, authentication, browser-connection, and external-service errors remain direct actionable errors because adapter repair cannot resolve them. When automatic repair is required, immediately show the returned `notification` as a non-blocking progress update, retain the workspace, follow `references/browser-repair-playbook.md` end to end, and resume from the retained browser and runner checkpoints. Do not pause for repair approval; the authorization boundary in the hard rules still applies.
- Two collector error codes are deliberate hard stops, not repair targets: `STICKY_TARGET_DATE_UNSUPPORTED` (see step 3) and `DETAIL_IMAGE_GALLERY_OVERFLOW_UNSUPPORTED` (a linked detail page whose image gallery shows a `+N` overflow badge; record that page's child inventory as failed through `inventory_failure` instead of repairing).
- Create the private runner workspace exactly as `references/runner-contract.md` specifies: pass a unique nonexistent child of a private temporary parent to `init`, which atomically creates and owns it — never pass an existing directory or symbolic link. Keep the inventory, raw transport URLs, working text, audit ledger, cache, and every captured representation there; every JSON input and referenced representation must resolve inside this workspace without symbolic links to outside paths. Use `assets/extraction-audit-template.md` for the temporary audit ledger and never place it in `output/`. The runner removes the marked directory after successful verification; on failure, retain it only when it helps diagnosis and report its path without exposing signed URL parameters.

### 3. Prove timeline coverage

- In the official UI, inspect and clear stale searches, tags, “只看星主”, member filters, and every other topic filter so the timeline includes every author's topics. Only after that visible confirmation, call `collectZsxqTimelineRangeWithAutoRepair` with `filtersClearedConfirmed: true`, the exact planet name, canonical group URL, Beijing platform date, runner workspace, and the live tab. Never set the flag merely to bypass `needs-filter-confirmation`; that status means the browser inventory is not allowed to start.
- When the collector returns `needs-top-confirmation`, visually load or dismiss every pending new-content batch through the official UI, confirm none remains, then rerun it with `topBoundaryConfirmed: true`. Never infer this confirmation from elapsed time or set the flag merely to continue. A visible top newer than the target date is already a sufficient upper bound; a top equal to or older than the target date requires this confirmation first, and only afterward may an older top prove a zero-topic target date.
- Require `status: complete` and proof that the stream crossed below the requested date before submitting the returned `coverage` and complete `inventory` object to the runner. Its exact top-level shape is `{ "topics": [...] }`; pass that object directly to `record-inventory`, never `inventory.topics`, and do not reconstruct or clean it by hand.
- Pinned topics are archived only through their normal position in the non-pinned stream; when that cannot be proven, the collector stops with the non-repairable `STICKY_TARGET_DATE_UNSUPPORTED` (a documented platform-behavior limitation). Report to the user that the day cannot be archived completely while that topic stays pinned, and do not enter the repair workflow.
- Timeline topics with a `+N` image-overflow badge are excluded from the inventory by decision and returned in `skipped_topics`. Report every skipped topic to the user in the final response; do not treat the badge as a defect or attempt manual enumeration.
- Submit the collector's complete source-inventory object once with `record-inventory`; the accepted top-level inventory is frozen, so start a new run rather than replacing it if that inventory was wrong, and do not start attachment extraction until the runner accepts it. Supply the raw stable platform identifier or permalink and let the runner derive each `topic_key`.
- Persist each attachment as a separate inventory entry with type, source ordinal, filename when exposed, stable platform identifier when available, and a transient `transport_url` when downloading requires one; supply every available raw value and never provide a precomputed identity. The runner derives `sanitized_source_url` and `source_identity` under the priority order in `references/runner-contract.md`; identity and inventory comparison never use the signed URL form, so signed-URL rotation between sessions cannot break a resumed run. Keep the full transport URL only in the temporary workspace.
- Associate every top-level image with one inventoried target-date topic before acquiring it, proven from that topic's own container, permalink/detail view, attachment order, or equivalent visible UI relationship. Never treat a page-wide asset inventory, a shared `images.zsxq.com` host, or the current scroll viewport as association proof. Exclude assets of other topics, avatars, group artwork, navigation, and other interface chrome before any screenshot or export.
- Within a linked page's main content, inventory every substantive inline image and directly embedded PDF as a child of that page attachment, following the one-time `record-web-inventory` rules in `references/runner-contract.md`: prove the complete child count during the page's single visit, freeze the child inventory before extracting the page body or any child, and submit `inventory_failure` with a concrete reason and localized reader note when the complete range cannot be proven — never claim zero without proof. For a Knowledge Planet detail link, call `collectZsxqDetailWithAutoRepair` and include every returned `files` entry in `dom_ordinal` order; a detail page's strict PDF cards are embedded children, never ignorable decoration. Treat decorative icons, avatars, navigation graphics, ads, and recommendation thumbnails as interface noise, and do not recursively follow hyperlinks discovered inside the page.
- For timeline topics, `image_count` and `image_count_evidence` come from the collector's verified gallery accounting; never re-count by hand.
- If the newest boundary cannot be established, the timeline cannot load far enough, chronology is inconsistent, or access hides an unknown number of topics, stop without creating or replacing the final file. Report why completeness cannot be established. A verified zero-topic day is valid only after crossing below the requested date.
- Submit the visible boundary evidence through `record-coverage`; a false coverage field fails closed per `references/runner-contract.md`.

### 4. Minimize repeated work

- Treat browser navigation as the scarce step. When opening a linked page, expand through the complete main-content boundary, submit its frozen child inventory, then capture its body, metadata, and exact assets before navigating away. The inventory call and extraction remain separate runner states but occur during one browser visit. Do not revisit that page solely to collect information or assets that were available during the first visit.
- Treat a browser asset list as inventory, not as a download queue. Never call an asset bundle with more than one remote image asset ID, never bulk-export every image on a page, and never select image downloads only by host, filename pattern, or rendered dimensions. Use a remote acquisition route only when the active tool provides an enforceable per-call deadline or cancellation; a request timeout that cannot cancel the underlying remote fetch is not enforceable.
- Use this per-image acquisition ladder: (1) the rendered topic preview or a locator screenshot of that exact image; (2) after one click into the platform image viewer, a locator screenshot of the clearer rendered image, rechecking the open viewer's exact image source and topic-local ordinal after the click; (3) one exact single-asset export through `scripts/zsxq-single-asset-export.mjs`. Stop acquiring at the first representation whose native pixels contain the needed information. If a clearer attempt fails or times out, do not retry alternate signed URLs, original-file variants, or equivalent transformations; retain the best already captured representation.
- When the native image contains small or dense text but whole-image visual verification remains uncertain, run `scripts/zsxq-image-tiles.mjs` against that exact workspace-local representation under the tile rules in `references/runner-contract.md`. This tile pass is mandatory before failure: never mark an image failed for small, dense, or compressed text while its native pixels have not yet been read tile-by-tile; if any tile remains unreadable, the image is failed.
- Keep one in-run binary cache through the runner's `cache-lookup` command under the reuse rules in `references/runner-contract.md`; never reuse a failed, partial, or uncertain result. There is no page cache: a repeated linked page is revisited and extracted again. Keep every occurrence-specific key in the audit ledger even when its verified payload is reused.
- Navigate authenticated pages sequentially so the browser session and timeline state remain deterministic. After source assets are local, independent images and PDF pages may be processed in bounded parallel batches, hashing and verifying each result separately.
- On a clearly blocked external page, stop retrying after the normal clean-page route and the one permitted browser route have both produced the same access-control result; record the failure and continue with the remaining inventoried content.
- These optimizations may remove duplicate navigation, download, OCR, and hashing work only — never reduce the inventory, skip an attachment, weaken verification, or change the one-level linked-page boundary.

### 5. Extract each topic in source order

Process the inventoried topics newest first, matching their source order. After freezing every linked-page child inventory for the topic and finishing all top-level and embedded extraction, write its JSON record according to `references/runner-contract.md` and submit it with `upsert-topic` (the runner accepts only the next source-order topic or a correction to the latest one). Use an ISO-8601 date-time with an explicit `Z` or numeric UTC offset. Use `status` after each topic to find pending child inventories and the resumable topic position.

When any payload is `failed`, store reliably recovered source fragments separately from `failure_reason`, with the exact UTF-8 `recovered_payload_sha256`, or no recovered hash with the literal `无可可靠恢复内容`; never mix the failure explanation into the source payload. This rule applies identically to topic bodies, images, linked pages, and PDF pages.

Extract every content type under the per-type rules in `references/runner-contract.md`; they are part of this skill's contract, and this summary changes none of them:

- **Topic body:** copy only the exact body carried by the collector's frozen inventory, without summarizing, "cleaning", re-extracting by hand, or guessing unreadable text (`[无法辨认]`); `present` requires the complete displayed body, and a truncated or uncertain body is `failed`.
- **Images, in attachment order:** any official-UI representation whose pixels make all substantive content readable is acceptable — representation quality and transport form never grade completeness. Extract semantic content text in natural reading order, keep interface chrome out and `source_account` separate, then perform the separate visual verification pass against the same representation; when small or dense text blocks whole-image proof, run the mandatory tile analysis before failing. `verified` requires that comparison to succeed; partial OCR is `failed`, and an unobtainable representation records failed extraction plus failed verification so the attachment stays visible as incomplete.
- **Linked pages:** prefer the clean-webpage extraction skill; extract title, original URL, available metadata, and the complete main body, then the frozen child inventory with the image and PDF rules. A clipped, paginated-but-unloaded, or paywalled body is `failed`, and one incomplete child fails the page.
- **PDFs:** follow the available PDF skill. Acquire an official member download only through the collector handshake in `references/runner-contract.md` — never reverse-engineer private APIs — and record a document-level access failure only when neither an official download nor another complete accessible representation exists. Prove `page_count` independently with evidence and preserve `第 N 页` page boundaries; a missing, duplicate, out-of-order, or out-of-range page makes the PDF failed.

### 6. Build the reader report through the runner

- Run `finalize`; do not compose either artifact manually. The runner re-resolves and re-hashes every checkpointed source file, renders the temporary audit ledger and the reader report, and applies the safe output-replacement rules — all specified in `references/runner-contract.md`. The audit ledger is process evidence, not user content.
- `assets/daily-source-template.md` is the reader-report contract: one section per inventoried topic and one subsection per attachment in original order, restricted to reader-facing content fields, with timestamps rendered as Beijing time `YYYY-MM-DD HH:mm:ss`. Process metadata — paths, keys, identities, ordinals, counts and evidence, asset URLs, hashes, dimensions, status fields, verification notes — never enters the reader report; only a linked page's original URL stays in its heading, because the shared link is part of the source content.
- For a failed item, the reader report keeps any reliably recovered fragment in its normal section, adds one short bracketed reader note at the exact missing location, and lists the affected items under `未能完整读取的内容` with the reader-relevant reason only. The report ends with exactly one runner-added hidden `zsxq-fetch` marker supporting safe reruns; a verified zero-topic day retains only the title and hidden marker.
- `completeness: complete` requires proven timeline coverage, every inventoried topic and attachment accounted for, every substantive payload fully extracted, and every image `verification_status: verified`. Source resolution, file fidelity, and acquisition route are never completeness gates; visual verification belongs to this extraction skill and must never be deferred downstream. When coverage is proven but any known item failed, the runner writes `<resolved-output-stem>.incomplete.md` instead and never overwrites a complete canonical report. `post_count` is the number of matching topics, including zero.

### 7. Verify and report

The runner performs verification during `upsert-topic` (field-by-field comparison of every extracted topic and frozen child inventory against the accepted source inventory, with runner-derived keys and identities) and `finalize` (re-resolving and re-hashing every checkpointed file, byte-exact audit-ledger round-trip, sanitized-URL enforcement, and the rerun-safety rules); the exact guarantees are specified in `references/runner-contract.md`. Do not duplicate them through hand-built Markdown or hand-computed hashes.

In the final response, report the resolved Beijing platform date, planet name, topic count, completeness value, extraction-failure count, every `skipped_topics` entry (author, Beijing timestamp, and that it was skipped for an image-gallery overflow), and the clickable absolute output path. Do not add a summary of the collected content.

## Hard rules

- Keep collected content local. Never publish, upload, email, or message it.
- Never use an unofficial Knowledge Planet API, reverse engineer requests, or introduce credentials.
- Never claim completeness unless an older topic or the exact absolute timeline-end marker proves the lower boundary and every inventoried item was accounted for.
- Never silently omit failed or ambiguous content. The only permitted exclusions are the collector's explicit `skipped_topics` (image-gallery overflow), and each of them must be reported to the user.
- Never render, report, or retain beyond the temporary workspace a full signed image or PDF transport URL, including its query, token, signature, or fragment.
- Never delegate image-to-OCR verification to a downstream analysis agent.
- Never include comments or replies. Changing that boundary requires updating this skill's agreed scope first.
- Automatically diagnose and repair browser-contract or collector-internal runtime exceptions after notifying the user with a non-blocking progress update. Preserve diagnostics and checkpoints, validate the repair fully, and resume from the retained position. Never commit, merge, push, publish, install dependencies, bypass access controls, or change unrelated files without separate authorization. The sole exception is `$fix-report` operating on its independently configured repository for the specified report-only commit and push.
